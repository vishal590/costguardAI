Fresh discovery and durable inventory are separate observations. Active resource listing/monitoring uses fresh discovery, not rows read from inventory storage. Existing raw resource identifiers in API responses, action selection and Resource objects remain unchanged.

The deployed inventory table retains its string partition key named resource_id. New schema_version 2 rows store that key as v2# plus SHA256 of canonical JSON [configured backend account, service, region, raw resource ID]. raw_resource_id separately retains the actual identifier; account_id/service/region describe the configured scope. This prevents collisions between equal raw names across those scopes without altering the table/index definition. Account scope comes from BACKEND_ACCOUNT_ID, not an independently verified STS identity; it must be exactly 12 digits before any inventory write is attempted. Missing storage/account configuration returns explicit persistence status while fresh discovery can still return observations.

Version 2 rows retain typed properties/tags/creation date, aware timestamp, numeric last_updated seconds, numeric observation_epoch_us and 90-day TTL. Conditional puts refuse to replace a row with an older batch persistence timestamp. This does not serialize discovery or prove which underlying resource state is latest, and equal timestamps can still overwrite. Stored counts represent acknowledged puts, not subsequent readback or a complete snapshot.

Legacy raw-key rows are neither migrated nor deleted. They can coexist until any existing TTL applies; TTL removal is asynchronous and not verified. No backfill, pruning, complete snapshot or absence-of-resources claim exists. A future storage consumer must explicitly choose schema 2 and raw_resource_id to avoid treating hashed keys as live IDs or mixing duplicate legacy observations. Existing active listing remains based on fresh discovery.

Unconfigured cases attempt zero writes; that count does not establish an empty inventory. Write failures do not silently become successful persistence or erase fresh read provenance.

## Bounded discovery listings (tasks 211-212)

Discovery listing adapters inspect at most five provider pages and retain at most 100 listed identities per operation. EC2 counts individual instances, not reservation envelopes. Nested CloudFront items and direct/unpageable address lists use the same selection boundary. Each operation reports service/operation, page/item limits, pages_read, listed_items_seen, retained_items, bound_reached, provider_listing_exhausted and observed_provider_pages/bounded_selection/unavailable_or_partial status. At an exact bound the next provider page is not fetched just to prove exhaustion; further listing coverage stays unknown. A reached bound does not prove more resources exist.

These are listing-operation bounds, not a total SDK-call or wall-clock budget. Per-resource metadata/tag calls, SDK retries, provider response size and adapter failures remain separate. A provider paginator exhausted within bounds does not establish complete inventory or verified metadata; some metadata adapters retain unavailable observations. Discovery has no cross-service continuation token yet: resources outside a bounded selection cannot be inspected through pagination on this endpoint. Service filters narrow adapter selection but do not guarantee that every resource within that service is inspected. Do not treat bounded inventory as a complete account or budget membership set.
