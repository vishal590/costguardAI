# Prevention audit history observations

Current local source, October 14, 2026, tasks 199-204. All testing/build/compilation/synthesis/browser/account/deployment validation remains deferred.

GET /api/prevention/history returns data_contract prevention_history_observations_v2, success, history, count, has_more, scope bounded_audit_record_selection and data_quality. Existing limit is 1-1000, default 100. Optional start/end accept the documented UTC-aware timestamp or inclusive calendar-date boundaries; invalid/reversed/excessive ranges are rejected. The frontend requests 50 rows per scan selection and supports first/next navigation.

Storage reads are capped at ten scan pages, each with Limit at most 100 and no more than the remaining returned-row capacity. The scan selects bounded storage rows, applies dates, sorts matching returned rows by timestamp and applies the return limit. It is not a globally latest selection or a complete action history. has_more means a next_cursor is available for the remaining storage scan; it does not guarantee additional date-matching rows. Optional cursor continues the same selection. Narrower dates change matches among inspected storage rows and do not guarantee that unscanned matches are found. Scan limits do not cap SDK retries or guarantee a wall-clock deadline.

Data quality includes status, page_limit/page_size/pages_read, examined_rows, invalid_rows, unavailable_timestamp_rows, matched_rows_in_selection, has_more_stored_rows and explicit unverified execution/savings scope. Missing/invalid timestamps remain unavailable and cannot match a date-filtered selection. Malformed summary rows are counted, not silently asserted absent. Failed reads remain 503; oversized JSON remains 413. An empty returned selection never establishes no earlier actions.

The scan projects only action/resource identifiers, timestamp, resource type/region, action/event/status, stored success/dry-run flags, optional finite nonnegative estimate, bounded error/message, account/mode/approval identifiers. Restoration snapshots, raw resource properties and unrelated audit fields are excluded from this report. Underlying rollback storage is unchanged. Summary identities are validated and never truncated into another identifier. Descriptive text is bounded. Stored success and estimates are assertions; execution_verified and monetary_savings_verified remain false.

Frontend history/rollback views show selection quality and refresh controls. The table labels stored events/status and explains unknown coverage. A recent timestamp only permits requesting a backend eligibility check; it does not establish permission, eligibility or completed restoration. No rollback or other resource operation was invoked during this implementation.

The cursor contains only the table action-id scan key and scope hash. It cannot establish a locked snapshot or global time order. First/next navigation clears old rollback selection; refreshing re-observes that scan selection. Filters changing or limit changing require restarting. Deleting/inserting/expiring rows between pages can alter coverage.
